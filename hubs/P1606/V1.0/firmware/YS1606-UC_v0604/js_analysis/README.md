# Hub 4 (P1606/YS1606) JavaScript Analysis

Source: `hubs/P1606/V1.0/firmware/YS1606-UC_v0604/usr/lib/p1606/p1606mq-dev.tar.gz`, which contains exactly two files - `index.js` (a 3.2MB, single-line webpack/Terser bundle) and `index.js.LICENSE.txt` (webpack's auto-generated third-party license manifest).

## Method

1. **Beautify, don't deobfuscate (yet).** `index.js` is *minified*, not *obfuscated* - short variable names and everything collapsed onto one line, but string literals, `require()` calls, and object/property names are all intact. Ran it through `js-beautify` (Node/npm, `npx js-beautify -f index.js -o index.beautified.js`) to get real line breaks and indentation back, no semantic loss.
2. **Split into individual webpack modules.** The bundle is one big `__webpack_modules__ = { <numericId>: (e,t,r) => {...}, ... }` map. Wrote a Python script to split it into one file per module ID. First pass had a boundary-detection bug - the split regex only matched arrow-function-style modules (`(e,t,r) => {`), silently swallowing the modules that use classic `function(e,t,r) {` syntax into whichever arrow-style module preceded them in the file (caught because one "module" was suspiciously 100KB+ for what should've been an 8-line helper). Fixed regex found **1,206 total modules**.
3. **Classify vendor vs. custom code, iteratively.** Fingerprinted modules against known bundled libraries using distinctive strings unique to each - Express and its ~20 internal packages, MQTT.js, `@grpc/grpc-js`, `ieee754`/`long.js`/protobuf runtime, `redis` (including its per-command definition files, which turned out to be individually tiny and needed their own detection rule), Luxon, underscore.js, `aedes` (the embedded MQTT broker), `qlobber` (MQTT topic-wildcard matching), a cron/schedule library, `jsonwebtoken`, `lru-cache`, `winston`, and Node core polyfills. All `jspb` (protoc-gen-js) generated files were identified separately by their `exportSymbol("proto....")` calls - this is where **ChirpStack's own generated gRPC API client stubs** live (see Findings). This took several rounds: an early pass left ~680 modules "unclassified"; by the end, refined signatures + explicit spot-checks brought that down to **216 modules of genuinely custom, YoLink-authored code** (~13,600 beautified lines) - everything else is vendor library internals.
4. **Read and manually restructure the architecture.** Walked the dependency graph outward from the bundle's real entry point plus every module containing explicit YoLink branding (`yosmart`, `YLTask`, `loraserver`, etc.), reading closely and hand-writing clean, renamed, commented equivalents - preserving the actual logic faithfully rather than "fixing" anything, including keeping the original bundle's own typos/bugs where found (flagged inline with `// [sic]`).
5. **Mechanically extract the repetitive remainder.** The 25 device-type command handlers (one per sensor/actuator class - DoorSensor, Thermostat, Lock, etc.) share two structural patterns but differ mostly in their specific opcode tables. Rather than hand-transcribing near-identical boilerplate 25 times, wrote a script to extract each one's full command table (opcode → method name, decode/encode registration) directly from source - see [`device-command-tables.md`](device-command-tables.md). This is genuine, complete, verified analysis of every device handler, just not hand-rewritten source for all of them.

## Findings

**ChirpStack, definitively confirmed - not just "LoRaWAN-adjacent."** Four independent pieces of evidence, weakest to strongest:
- Config file shape: `/etc/loraserver/loraserver.toml` with a `sqlite://` backend and `network.net_id` field matches the open-source LoRa Server/ChirpStack project's actual config format.
- MQTT topic convention: `application/+/device/+/event/up` is ChirpStack's own default uplink-event topic, verbatim - and it's what `loraserver-pipe.js` (the actual bridge between ChirpStack and this app) subscribes to.
- The default gRPC auth token is a real JWT (`config.js`) whose payload, decoded, is `{"aud":"chirpstack","iss":"chirpstack","sub":"<uuid>","typ":"key"}`.
- `chirpstack-subnet.js` (`YLSubnet`) actively manages ChirpStack Tenants, DeviceProfiles, Applications, and Devices via generated gRPC client stubs (the large `proto.api.*` bundle modules identified during vendor triage) - this Node process is ChirpStack's primary control-plane client, not a passive integration.

**Two complete YoLink device catalogs, recovered in full.** `device-type-from-appeui.js` decodes a device's 4-hex-digit model key (from its AppEUI) into a device-class string - this is effectively YoLink's internal product-numbering rosetta stone (`"77"` family → doorSensor, matching P0706/YS7704 elsewhere in this repo; `"80"` family → THSensor, matching YS8003/8004/8005/8006). `device-session-store.js` separately maps each device-class string to its default LoRaWAN device class (A/C/D), including several literal-AppEUI-prefix overrides for specific model variants.

**Hardcoded local MQTT broker credentials - now three separate findings, not one.** `mqtt-local-broker.js` embeds a static username/password table for four internal client identities (`loraserver`, `integration`, `as`, `yaochi`) that gate who may connect to the hub's own embedded MQTT broker (`aedes`, running in-process). `general-client.js` (module 84903) separately hardcodes the password for its own "as" MQTT identity (`sub-c-2a6a8e14-301b-11e5-b3fa-02ee2ddab7fe`) when connecting to that same broker. `lcsubnet-token.js` (module 85672) hardcodes yet another credential pair - a static issuer id + signing key for an internal "default_api" JWT issuer, whose actual consumer hasn't been traced yet. All three are compiled into every hub running this firmware build, not generated per device. **Not yet verified:** whether the local broker (started via plain `net.createServer(...).listen(18080)` with no explicit bind host) is reachable from the LAN or only from localhost.

**The cloud MQTT bridge and local-API auth, now mapped.** `mqtt-remote-broker.js` (module 65446) is the *other* MQTT connection - not the embedded local broker, but the outbound connection to YoSmart's cloud MQTT broker, authenticated with a per-gateway (not hardcoded) password from `gwConfig`. It carries admin commands (routed into `hub-remote-commands.js`'s ~25-command registry: reboot, wifi, firmware update, Matter, local-automation CRUD, and a raw `hub._cli` shell-command passthrough), downlink LoRa messages, and legacy-hub-bridge traffic. Separately, `oauth2-provider.js` + `lcsubnet-token.js` + `lcsubnet-auth.js` implement a full OAuth2/JWT flow for the LCSubnet local HTTP API - but every credential in it (client secret, access/refresh token signing keys) reduces to `MD5(subnetId:familyId[:loraNetId])`, the same "secret" scheme used throughout this bundle. Anyone who knows a hub's subnet id and family id (both visible in ordinary cloud API responses) can mint their own valid access token for that hub's local API without ever contacting the hub.

**Firmware update mechanism has no signature verification.** `upgrade-task.js` (module 88196), invoked via `hub-remote-commands.js`'s `"update"` RPC command, downloads an arbitrary URL to `/tmp/ota.bin`, optionally checks its MD5 (skippable entirely by passing the literal string `"ignore"` as the md5 parameter), then untars it and installs every `.deb` via `dpkg -i` and runs every `.sh` as `/bin/bash`. Whoever can reach the `"update"` command or `hub._cli` (gated only by the local/cloud MQTT transport auth already discussed above) can get arbitrary code execution as whatever user runs this Node process.

**The LAN-vs-cloud bridging mechanism is now fully traced, end to end.** `gateway-lora-receive.js` (module 36248) is the actual dispatch point for every uplink: a `JoinRequest` is routed to the LOCAL embedded ChirpStack (not the cloud) if its DevEUI is already known to this hub's own subnet; a data uplink is routed locally if its DevAddr falls in the LoRaWAN Alliance's "locally administered" NetID range (`lora-net-id.js` / `lora-uplink-metadata.js`, NetID types 6-7). This is the concrete mechanism behind the `yolink-hub.js` P1605-bridge finding from the previous pass - a bridged legacy hub broadcasts with a LAN-range DevAddr, so its traffic never leaves the P1606 hub at all.

**Two more LAN-only HTTP surfaces found, beyond `/_internal`.** `wifi-config-api.js` (module 34121, mounted at `/api/v1`) exposes network status and wifi-station configuration (scan/connect/exit-AP-mode) to anything on the same LAN segment, no auth token, the same hostname-allowlist pattern as `/_internal` - almost certainly what a companion setup app talks to during initial provisioning over the hub's own AP-mode hotspot. `open-api-routes.js` (module 50741) is the actual Express mounting for the public `/open/yolink/v2/api` and `/open/yolink/token` endpoints, tying `http-api-wrapper.js`, `oauth2-provider.js`, and `message-dispatcher.js`'s `HandlerDispatcher` together - the missing link that makes the whole HTTP API story concrete rather than inferred.

**A localhost/LAN diagnostics HTTP endpoint exists at `/_internal`.** `internal-diagnostics-api.js` (module 26807) exposes hub status, subnet info, and per-device cached state, gated only by a hostname check (`127.0.0.1` or `192.168.*`) - no token required. Reachable by anything on the same LAN segment, not just the hub itself.

**A second REST API surface exists per-device-type, alongside the LoRa command layer.** `api-handler-base.js` + `lock-api-handler.js` (modules 21285/17045) show the hub also exposes an HTTP API (the `/lcsubnet/dpf/...` namespace referenced in `lcsubnet-api-client.js`) with one handler class per device family - `LockAPIHandler` is the only concrete example found so far (password/PIN management, state get/set), but the base class's dispatch pattern implies sibling handlers for other device types exist elsewhere in the still-unexamined remainder.

**Hub cloud-registration flow, fully mapped.** `hub-provisioning.js`: on first boot, the hub signs a JWT over its own hardware ID (`system-info.js`'s `getHWId()` - itself just an MD5 of the CPU serial + eMMC CID, not anything secure-element-backed) and POSTs it to `https://us.yosmart.com/dar/registerHub`. The signing key is `MD5("ys.YoSmart.appId/d88b4c1606000000")` - computable by anyone who knows the (now-known) scheme, not a per-device secret negotiated beforehand.

**P1606 can bridge older YoLink hubs into itself.** `yolink-hub.js` represents a *connected legacy hub* as just another managed "device," and specifically checks whether the connecting hub's device ID matches `/^[\w]{6}1605/` to decide whether to enable automation for it - strongly suggesting P1606 was built, at least partly, as a bridge to bring the previous hub generation into the same ChirpStack-backed system, not as a fully standalone replacement.

**25 device types, fully cataloged.** See [`device-command-tables.md`](device-command-tables.md) for the complete opcode/command table of every device-type handler in the bundle - including the IR-blaster (`InfraredRemoter`, the exact product from the writeup's §1), the THSensor family (matches `sensors/YS8003`), and several device types (P5005/P5006/P5007/P5009/P7616-prefixed "Register" classes) that don't obviously map to a product already documented elsewhere in this repo and might be worth chasing down.

**Hardware confirmations that corroborate the rest of this repo:**
- `lora-transport.js` logs `"Connected to the SX126X module"` on connect - matches the LLCC68 (SX126x-family) identification already made via FCC teardown photos (see `fcc_filings/2ATM71603M`).
- The status-LED logic (`hub-provisioning.js`) drives a `lte_led` and reads an `e.lte` status field - confirms the "Local Hub" product's advertised LTE/cellular capability at the code level, not just the marketing page.
- Local SQLite path defaults to `/var/lib/yosmart/p1606_local.db`; log directory defaults to `/tmp/p1606`; Redis defaults to db 9.
